# Verification and evidence ecosystems: facts for Shape's claim-and-evidence ledger

Researched 2026-10-25. **[V]** marks a vendor or author self-report. **[L]** marks a measurement from this repository. *(older)* marks material from before 2025 that is still current. Lines starting "Inference" are my own reading of the cited facts.

## 1. Cedar: verification-guided development and policy comparison

- **The process.** Verification-guided development (VGD) has four parts: an executable Lean model with proofs, production code in Rust, differential random testing (DRT) of the Rust code against the model, and property tests for the parts the model leaves out. "A new version of Cedar isn't released unless its model, proofs, and differential tests are up to date" [V] *(older)* — [AWS blog](https://aws.amazon.com/blogs/opensource/lean-into-verified-software-development); [FSE'24](https://dl.acm.org/doi/abs/10.1145/3663529.3663854)
- **Size and speed.** In 2024 the Lean model was 1,673 LOC plus 5,714 LOC of proofs. Rust had 15,693 LOC of production code and 20,458 LOC of tests. The parser is not modelled ("unclear what properties we could prove"). During DRT the median Lean authorizer call takes 6 µs against 10 µs for Rust. Checking all proofs and compiling the models takes about 3 minutes *(older)* — [FSE'24 PDF](https://cdn.amazon.science/d3/86/99db1aa142ffb6981d86dc849e4c/how-we-built-cedar-a-verification-guided-approach.pdf)
- **Bugs found and missed.** Proofs found 4 validator bugs, including a non-termination bug. DRT and property tests found 21 more. DRT missed the non-termination bug, parser crashes on malformed input, and bugs in APIs it never called. Each target is fuzzed 6 hours a day on 4 vCPU — same PDF
- **SymCert** (FMCAD 2026) is a Lean framework for verified SMT-based policy analyses.
  - Proofs took about 5× the person-hours of models: the symbolic compiler took 81 hours to model and 327 to prove.
  - Five production analyses (denies-all, allows-all, implies, equivalence, disjointness) took one day.
  - Each extension cost SymCert 4–8 days; the datetime extension cost the core model 26 days.
  - The SMT solver is trusted, not verified. Production runs a Rust port, with Lean as the oracle for daily DRT. Four developers made the extensions.

  — [SymCert PDF](https://repositum.tuwien.at/bitstream/20.500.12708/230492/1/Torlak-2026-SymCert%20Verifying%20SMT-Based%20Policy%20Analyses-vor.pdf)
- **Shipped.** The `cedar-policy-symcc` 0.7.0 crate ships `check_implies` (subsumption), always-allows, always-denies and never-errors — [docs.rs](https://docs.rs/crate/cedar-policy-symcc/0.7.0/source/README.md). The Lean specification also generates conformance tests for cedar-go — [CNCF issue](https://github.com/cncf/sandbox/issues/371)
- **Zelkova precedent.** AWS's Zelkova reached about a billion SMT queries a day by building domain abstractions and "eliminat[ing] specifications": customers ask fixed questions rather than write specs *(older)* — [Rungta, CAV'22](https://www.amazon.science/publications/a-billion-smt-queries-a-day). IAM Access Analyzer's `CheckNoNewAccess` compares an updated policy with a reference policy in CI. FAIL means the new policy "might allow new access", and each check is billed *(older)* — [API](https://docs.aws.amazon.com/access-analyzer/latest/APIReference/API_CheckNoNewAccess.html); [blog](https://aws.amazon.com/blogs/security/introducing-iam-access-analyzer-custom-policy-checks/)

Inference: at Cedar's ratios (a model about 1/10 the size of production code), a Lean model of `shp check`'s rule core is affordable. Shape already has a DRT seed corpus: about 82,000 E10 mutants with byte-identical reruns [L] ([E10](../../experiments/verus-probes/e10/REPORT.md)). Detecting that a claim has loosened is the same question as `CheckNoNewAccess` and `check_implies`. Zelkova's lesson is to offer fixed questions, not user-written specs.

## 2. Verus in 2026

- **Users.** AWS uses Verus for "key primitives" of the Nitro Isolation Engine and other internal infrastructure [V]. Open-source users include Atmosphere, Anvil, Vest, Verdict and CapybaraKV — [Amazon Science, 2026-08-31](https://www.amazon.science/blog/developing-provably-correct-rust-code-with-verus). Atmosphere (SOSP'25) has a proof-to-code ratio of 7.5:1 — [project page](https://mars-research.github.io/projects/atmo). Asterinas, which verifies parts of its kernel with Verus, is "not yet production-ready" — [;login:](https://www.usenix.org/publications/loginonline/asterinas-rust-based-framekernel-reimagine-linux-2020s)
- **Releases.** Verus ships weekly, date-versioned releases — [releases](https://github.com/verus-lang/verus/releases)
- **PDD Kit** (GitHub Next with Microsoft Research) entered research preview on 2026-10-21. A team plans in Chopin, an agent proposes a Verus spec, and a human approves "the spec, not the code". Verus then proves the code meets the spec. Where proof is impossible, the kit falls back to "tests and computer-use agents". It supports Rust only [V] — [GitHub Next](https://x.com/GitHubNext/status/2112936525457740139); [recap](https://automater.ai/news/github-next-pdd-kit-verus-proof-verification/). I found no public repository, and githubnext.com/projects/pdd-kit returns 404.
  - The unrelated pdd-kit.dev ("Product-Driven Development") keeps a git-tracked product model, and its verify step "never persists a workflow ledger" — [changelog](https://pdd-kit.dev/changelog)
- **Trust markers.** Unproven assumptions enter through `assume`, `admit`, `external_body`, `assume_specification` and `external` — [guide](https://verus-lang.github.io/verus/guide/tcb.html). I found no official trust-base report or spec-fingerprint tool; KVerus extracts symbols through verus-analyzer ([KVerus](https://arxiv.org/html/2605.03822)), and this repository's `vprobe` fingerprints contracts with `verus_syn` [L].
- **AI proving.** In the VeruSAGE study, models without a cheat checker cheated on 2–14% of tasks. They added `assume`/`admit`, marked functions `external_body`, or weakened specs. With the checker, cheating fell below 1.5%. Sonnet 4.5 proved 81% of 849 system tasks, which average 496 lines of spec each. It also flagged 5 Atmosphere specs that needed adjustment, all confirmed by experts — [VeruSAGE](https://arxiv.org/html/2512.18436v2). The KVerus authors write that "toolchain updates can break" proofs and that "proof generation is also proof maintenance" — [KVerus](https://arxiv.org/pdf/2605.03822)
- **This repository's measurements** [L], over 8 Verus systems and 4,565 commits ([verus-probes](../../experiments/verus-probes/README.md)):
  - 53% of edits to verified functions change the contract.
  - In 3 repositories, 45–100% of contract changes come from Verus migration commits.
  - In 5 of 8 repositories, 83–98% of commits carried an outstanding `assume` or `admit`.
  - A solver check of whether an edited contract is looser raised 0 false alarms on migrations and flagged 11 of 14 dropped clauses. The other 3 were implied by the rest.

## 3. Lean 4 and AI provers

- **Industry.** The Lean FRO has 20 engineers, more than 9,000 GitHub repositories depend on Lean, and its industry users include AWS, Google, Microsoft and Mistral — [Ullrich, 2026-06-04](https://lean-lang.org/presentations/20260604_DFMD). Amazon gives the FRO long-term funding and uses Lean in Bedrock AgentCore, SampCert and Neuron — [Amazon, 2026-07-26](https://www.amazon.science/news/amazon-is-investing-in-the-lean-focused-research-organization). AWS's Waimea, a verified compiler for Trainium, is about 500,000 lines of Lean — [de Moura, Aug 2026](https://leodemoura.github.io/static/marktoberdorf2026/lecture4/index.html)
- **Competition maths is saturated.** Several systems have solved all 672 PutnamBench problems; NEAR AI with DeepSeek V4 averaged $0.17 a problem (2026-07-19). Seed-Prover 1.5 solved 581 (2025-12) — [leaderboard](https://trishullab.github.io/PutnamBench/leaderboard.html). AlphaProof was published in Nature on 2025-11-12 — [Nature](https://www.nature.com/articles/s41586-025-09833-y)
- **Software proofs are not saturated.**
  - VeriSoftBench (500 proof obligations from 23 repositories): Gemini-3-Pro is best at 41%, and Goedel-Prover-V2 scores 0% with the full repository as context. Aristotle scores 69% on an easier subset, where Gemini scores 65% — [arXiv 2602.18307](https://arxiv.org/html/2602.18307v1)
  - VERINA: o3's proof success was 4.9% when the benchmark was released — [ICLR'26](https://proceedings.iclr.cc/paper_files/paper/2026/hash/41b8c80f9113b9f8e2e129447221682a-Abstract-Conference.html). Aristotle later reported 96.8% [V] — [Harmonic](https://www.harmonic.fun/news/verina-benchmark/)
  - VeriBench: agents' end-to-end scores are at most 0.42, and how much of the reference theorem their specs cover "stalls … at ≤0.11" — [ICML'26](https://icml.cc/virtual/2026/82455)
- **lean-zip.** Claude ported zlib to Lean with about 32,000 lines of proof and no `sorry` — [repo](https://github.com/kim-em/lean-zip). Fuzzing then found a buffer overflow in the unverified Lean runtime — [kirancodes, 2026-04-13](https://kirancodes.me/posts/log-who-watches-the-watchers.html)
- **Proof validation tiers.** The Lean manual grades checks by threat model. `lake build` protects only against honest mistakes. `#print axioms` also exposes `sorryAx`, custom axioms and `Lean.trustCompiler`, and `leanchecker` replays the compiled `.olean` files. The "gold standard", `lake comparator`, checks the proof against a trusted challenge statement, permitted axioms and external kernels. The manual counts "un-reviewed AI-generated proofs" as potentially malicious — [Validating a Lean Proof](https://lean-lang.org/doc/reference/latest/ValidatingProofs)
- **Kernel soundness.** In July and August 2026, OpenAI's internal models found kernel and runtime bugs (including one in GMP 6.1.2) and used each to prove `False`. The fixes shipped in v4.33.1 — [postmortem](https://leodemoura.github.io/blog/2026-8-24-postmortem-for-the-kernel-soundness-bug-hunt/). v4.35.0 adds `lake check --paranoid` with four extra kernels. One, con-leche, is proven consistent and was built by Claude under supervision — [2026-10-15](https://leodemoura.github.io/blog/2026-10-15-lean-now-ships-with-verified-kernels/)

## 4. Attestation formats

- **in-toto Statement v1.** A statement has `subject[]` (artifacts matched "purely by digest" and assumed immutable), a `predicateType` URI and a `predicate` — [spec](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md). in-toto graduated in the CNCF in 2025 — [CNCF](https://www.cncf.io/projects/in-toto/)
- **Vetted predicates** include SCAI, Test Result, SVR, VSA and SLSA Provenance — [list](https://github.com/in-toto/attestation/blob/main/spec/predicates/README.md).
  - SCAI v0.3 holds `{attribute, target, conditions, evidence}` entries plus a `producer`. It covers "properties tested via static analysis" — [SCAI](https://github.com/in-toto/attestation/blob/main/spec/predicates/scai.md)
  - Test Result records a result, the configuration and the passed and failed tests — [spec](https://github.com/in-toto/attestation/blob/main/spec/predicates/test-result.md)
- **No built-in freshness.** SVR v0.2 records a versioned `verifier.id`, policy digests, `timeCreated` and `properties`. Time limits are naming conventions that consumers enforce: `VERIFIER_VULN_SCANNED_1` means scanned within one day — [SVR](https://github.com/in-toto/attestation/blob/main/spec/predicates/svr.md). SLSA's VSA adds `inputAttestations` and `verificationResult` — [VSA](https://slsa.dev/verification_summary/v1). SLSA v1.2 (2025-11-24) added Source VSAs, which summarise a revision's change history — [source track](https://slsa.dev/spec/v1.2/source-requirements)
- **Signing and tooling.**
  - `actions/attest` signs custom predicates with keyless Sigstore certificates, and `gh attestation verify` checks them.
  - Private repositories need GitHub Enterprise Cloud — [actions/attest](https://github.com/actions/attest)
  - Sigstore's Rekor v2 log reached general availability in October 2025, but sigstore.dev still defaults to v1 — [GA](https://blog.sigstore.dev/rekor-v2-ga); [2026-06-28](https://blog.sigstore.dev/rekor-evolution)
- **Findings formats.** SARIF 2.1.0 gives each result a `baselineState` (new, unchanged, updated or absent) and `suppressions` with a status and a justification. Those fit an obligation's lifecycle and attestations — [OASIS](https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html). OpenSSF Scorecard v5 replaced aggregate scores with stable atomic "probes" *(older)* — [OpenSSF](https://openssf.org/blog/2024/04/17/beyond-scores-with-openssf-scorecard-granular-structured-results-for-custom-policy-enforcement)

Inference: Shape evidence can reuse these predicates. SCAI fits proofs and mapper facts (attribute = claim ID, target = code fingerprint, conditions = toolchain and assumptions). Test Result fits property tests, and SVR fits `shp`'s own verdict. If subject digests are Shape's normalised fingerprints, evidence goes stale whenever the code changes. Reuse buys signing, a CI identity on each record, storage and verification tooling. Shape must still define expiry, claim meaning and loosening.

## 5. Certificate checking

- **The principle.** Checkers "are usually much simpler than the algorithms they check", so verifying the checker is easier than verifying the algorithm *(older)* — [McConnell et al.](https://www.sciencedirect.com/science/article/pii/S1574013710000560). In CompCert, an unverified compiler pass plus a verified validator gives guarantees as strong as a verified pass *(older)* — [Leroy](https://arxiv.org/html/0902.2137v3)
- **SAT solving.** The SAT Competition's main track requires proofs of unsatisfiability, checked by verified checkers (cake_lpr, GRAT, CakePB). Buggy solvers are disqualified. The checker gets 45,000 s against the solver's 5,000 s — [rules](https://satcompetition.github.io/2025/output.html); [results](https://satcompetition.github.io/2025/satcomp25slides.pdf)
- **Inside Lean.** `bv_decide` hands the goal to CaDiCaL, which is untrusted and emits an LRAT certificate. A checker proven correct in Lean validates it, which puts the Lean compiler in the trusted base — [API](https://lean-lang.org/doc/api/Lean/Elab/Tactic/BVDecide.html); [v4.12](https://lean-lang.org/doc/reference/latest//releases/v4.12.0)
- **Datalog and binaries.** A Lean-verified checker validates proof trees from the Nemo and Soufflé Datalog engines — [ITP'25](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ITP.2025.36). seL4's binary validation removes GCC from the trusted base — [seL4 2026](https://sel4.systems/Summit/2026/posters/binary-verification.pdf)
- Inference: this pattern wins when the engine is large, heuristic or fast-moving, and each result has a certificate that is cheap to check. Cedar chose the reverse: it verified the model, trusts the SMT solver, and tests the Rust code (§1).

## Synthesis for the ledger strategy

- **Supports.** Proofs are getting cheap to produce (81% of Verus system tasks; lean-zip). The scarce part is knowing whether specs are adequate and the trusted base is sound: spec coverage of at most 0.11, cheating on 2–14% of tasks, 5 flawed Atmosphere specs, AI-found kernel exploits. PDD Kit already mixes evidence kinds. Loosening checks have precedent: `CheckNoNewAccess`, `check_implies`, E3.
- **Refines.** Key freshness to fingerprints and a pinned toolchain, not to time. Give evidence tiers modelled on Lean's validation levels, and record the checkers used. Treat missing evidence as an obligation owed, not a failure, because `assume`/`admit` debt is chronic. Limit a Lean model to rule evaluation, as Cedar left out the parser.
- **Undermines.** A comparable agent tool deliberately re-derives findings instead of keeping a ledger, so persistence must justify itself; only signatures and human judgements cannot be re-derived. in-toto has no expiry and private-repo attestation needs GitHub Enterprise Cloud, so signing should stay optional. Cedar-level proof cost would tax every semantic change. "Proved" covers only what the spec says, as lean-zip's runtime overflow shows.
