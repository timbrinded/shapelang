# Bend Offers Shape Ideas, Not Leverage

Integrating Bend, or running any part of Shape on HVM, would not multiply Shape's force. On current evidence it would subtract from it, though three of Bend's ideas are worth borrowing in plain TypeScript. Shape's own profile decides the question: a full `shp check` of the repository's 242-file model takes about **0.75 s**, parsing and module loading take roughly **85%** of that, and all 18 semantic rules take **8 ms warm**, so even an infinitely fast rule engine would save about 1%. "Bend" has also changed underneath the question. **Bend 2**, released on 2026-09-17, is a dependently typed proof language on a conventional C/JS runtime that **no longer uses interaction nets**; the HVM line has stalled, and HOC's superposition synthesizer, SupGen, has never shipped. Native Bend cannot build for Windows, which Shape releases and verifies on every tag, and its JavaScript target, the only route that keeps Shape's single binary, runs on one core and broke its host interop in a patch release. Every job Bend might do for Shape (rule evaluation, incremental re-checking, mutation batches, claim synthesis, proving the checker) has a cheaper alternative with better evidence, and Shape already owns some of them: its in-process incremental checker runs mutants **17–23x faster** than the CLI. What transfers is conceptual: Bend 2's `LAWS.bend` proof gate supports Shape's thesis that reviewed claims belong beside code, its map-and-fold style points to order-independent rules and a fix for the one superlinear rule, and its `@unsafe` escape hatches are trust markers Shape could govern the way the Verus probes governed `external_body`.

## Rule evaluation takes about 1% of a check, so there is nothing to speed up

Shape's checker has five phases. It parses every `.shape` file with a Langium grammar, then lowers the result into one `Model` made of typed indexes and a provenance-carrying `Fact[]`. It then runs 18 ordered semantic checks plus `checkBindings`, and sorts diagnostics by kind and rendered text in codepoint order ([checker-pipeline.md](../docs-site/src/content/docs/inside-shape/checker-pipeline.md)). No rule reads `model.facts`. Rules read the typed indexes, and facts leave the checker only on request ([fact-lowering.md](../docs-site/src/content/docs/inside-shape/fact-lowering.md)). The repository's own model was profiled on 2026-10-24 on a 4-vCPU Linux host with Bun 1.4.2. It has 242 files, 1.59 M characters, 15,166 facts and 1,378 hyperedges. On it, `shp check` took a median of **0.747 s from source and 0.695 s as a compiled binary** ([local profile](../research_notes/Bend%20and%20HVM%20for%20Shape/shape_codebase_fit.md)):

| Phase | Cold (ms) | Warm (ms) |
|---|---:|---:|
| Module import | 109 | — |
| Read and parse, 242 files | 543 | 348 |
| Lower to `Model` and facts | 70 | 22.6 |
| All 18 semantic rules | 35.0 | **8.0** |
| `checkBindings` plus formatting | 0.4 | — |

A separate sampled CPU profile gives the same picture. About **57%** of samples fall in Langium and Chevrotain parsing and CST building, 4–6% in lowering, and **under 2%** in the rule modules ([CPU profile](../research_notes/Bend%20and%20HVM%20for%20Shape/alternatives_and_opportunity_cost.md)). That settles the main question before Bend's merits come up at all. Any alternative rule backend can remove at most 8 to 35 ms from a 750 ms run. Shape's own policy for reopening the rule-engine decision requires that "representative profiling identifies semantic rule evaluation, rather than parsing or lowering, as a meaningful bottleneck" ([rule-evaluation.md](../docs-site/src/content/docs/inside-shape/rule-evaluation.md)). The profile shows the opposite. Outside evidence agrees on where the lever is: TypeScript 7's independently measured gains come mostly from native code (**3.1–3.9x**), with parallel checking adding only **1.4–2x**, an amount that "grows with the codebase" ([stevenpg.com](https://stevenpg.com/posts/typescript-7-go-compiler-benchmark/)).

Scaling tests confirm that rules stay cheap. On a synthetic 20,000-component model with 60,000 `calls` edges, the rules took **1.03 s against 26.7 s of parsing**. The one real hotspot appears only in a failing model with a single giant strongly connected `calls` component. There, `checkHypercycles` took **442 ms at 1,000 nodes, 3.0 s at 2,000 and 33.2 s at 5,000**, roughly N^2.7 ([local profile](../research_notes/Bend%20and%20HVM%20for%20Shape/shape_codebase_fit.md)). The cause is algorithmic. To pick the canonical shortest cycle, the rule runs a breadth-first search from every vertex in each cyclic component, then compares candidates by length, vertex sequence and relation name ([rule-evaluation.md](../docs-site/src/content/docs/inside-shape/rule-evaluation.md); [relations.ts](../packages/shp-checker/src/checker/rules/relations.ts)). Selecting a minimum under a total order lets each search stop once its partial cycle exceeds the best found so far. That is a TypeScript fix, not a case for a new runtime, although the pruning's effect has not been measured yet.

Batch workloads are the only place where Shape runs many near-identical checks, and they are small. The E10 mutation study checked about **82,000 mutants**: 79,415 add-effect, 181 remove-grant, 502 add-`calls` and 1,876 add-`provides`, plus probes. The bulk operator was batched, and reruns were byte-identical ([E10 report](../experiments/verus-probes/e10/REPORT.md)). The existing `IncrementalShapeChecker` reparses only the changed document. Loaded with all 242 documents and re-checked after each one-edge mutation, it ran at a median of **32.1 ms per mutant on `runtime.shape` and 43.9 ms on `checker.shape`**. That is 17–23x faster than a fresh process, and it killed 31.5% of mutants against E10's 34.3% score for the same operator ([local profile](../research_notes/Bend%20and%20HVM%20for%20Shape/shape_codebase_fit.md)). At that rate even all 82,000 mutants, unbatched, would take about 45–60 CPU-minutes.

There is also a cost at the boundary. Any backend that takes facts as input (Bend, Datalog or the Rust kernel) needs the projected fact stream. Turning on `includeFacts` raises `checkLoweredShapeModel` from **60 ms to 1,099 ms**, and 958 ms of that is sorting. The sort uses `compareCodepointStrings`, which calls `Array.from` on both strings in every comparison ([local profile](../research_notes/Bend%20and%20HVM%20for%20Shape/shape_codebase_fit.md); [shape-strings.ts](../packages/shp-checker/src/shape-strings.ts)). Feeding data to a new engine therefore costs about 30 times more than the lowering and rule work the engine would replace. The Rust/WASM semantic kernel's own README already says its fast numbers "establish feasibility and scaling data, not a production speedup" ([semantic-kernel README](../experiments/semantic-kernel/README.md)).

## Today's Bend is a five-week-old proof language that has left HVM behind

Most commentary about Bend describes a language that no longer exists. Bend 1 ran on HVM2. It launched in May 2024, its last release was 0.2.38 in February 2025, and it is now superseded. Bend 2 is a rewrite from scratch, committed on 2026-08-13 and released on 2026-09-17. It had produced **32 release tags in about five weeks**, up to v2.0.39 on 2026-10-23 ([bendlang/bend](https://github.com/bendlang/bend)). Its README says plainly: "Bend 2 is a new language. Bend 1 programs and HVM do not carry over" ([README](https://github.com/bendlang/bend#limitations)). Its runtime paper says it more directly: "Readers of the author's earlier runtimes may expect interaction nets here; there are none" ([BendRT paper](https://raw.githubusercontent.com/bendlang/bend/main/paper/BendRT.pdf)). Meanwhile, the HVM line has stalled. HVM2's last commit was on 2024-08-21. HVM3 has had one commit in 2026. HVM4 still says "you're here before launch. Use at your own risk", has had **no commits since 2026-05-29**, and has **no LICENSE file in any commit** ([HVM2](https://github.com/HigherOrderCO/HVM2); [HVM4](https://github.com/HigherOrderCO/HVM4)). Integrating "HVM" today means picking an artifact that is either unmaintained or unlicensed. Integrating "Bend" means Bend 2, a different proposition from the GPU-parallel interaction-net language the question imagines.

Bend 2 is a pure, affine, dependently typed language with Python-shaped syntax. It has `law` declarations proven by same-named definitions, and parallelism comes from explicit, balanced fork-join calls rather than automatic splitting ([GUIDE.md](https://github.com/bendlang/bend/blob/main/guide/GUIDE.md)). The vendor's own limitations list hits Shape's needs directly. Numbers are **Nat, U32 and F32 only**. Strings are "linked lists of characters, so text processing is slow", and there is no JSON or regex. There are no tactics or proof search. The compiler is "**99% AI-written and not yet fully audited**", and the everyday checker "has no proof and may have bugs" ([README](https://github.com/bendlang/bend#limitations)). The proof kernel behind `--verdict`, BendTT, is verified in Lean and carries a $10k bounty. The parser and the translation into that kernel are not proven ([Taelin on X, 2026-09-27](https://x.com/VictorTaelin/status/2104240438127288652)).

Speed figures are vendor-pinned. On HOC's own Apple M4 Max benchmarks, single-core Bend 2 takes **0.70x to 4.4x the time of C**, and 16 cores give about 10–12x. The GPU dominates uniform numeric work (n-body in 0.059 s against 5.1 s for C), but it is slower than the parallel CPU on 5 of 16 workloads ([M4 Max pin](https://github.com/bendlang/bend/blob/main/bench/runtime/_pin_/apple_m4_max.txt)) and on 10 of 17 on a plain M4 ([M4 pin](https://github.com/bendlang/bend/blob/main/bench/runtime/_pin_/apple_m4.txt)). Independent evidence is thin. One porting study concluded that "no number here shows Bend faster than Rust on the same work" ([AkitaOnRails](https://akitaonrails.com/en/2026/09/19/new-ai-language-just-released-bend-2)), and community issues document CUDA slowdowns of 4x to 200x ([bendlang/bend issues](https://github.com/bendlang/bend/issues)).

Set against Shape's non-negotiable constraints, native Bend fails before performance becomes relevant:

| Shape constraint | Native Bend 2 (C, CUDA, Metal) | Bend 2 JS/ESM target | HVM2 / HVM4 |
|---|---|---|---|
| One self-contained `shp` per platform, **Windows x64 included**, verified each release | Fails: "No Windows (WSL works)"; needs clang 14+ to build | Bun could plausibly bundle it into `bun build --compile`; untested | Fails: no Windows; HVM4 unlicensed |
| Byte-stable, deterministic diagnostics | Values deterministic by design; F32 output differs across backends | Same | Strongly confluent |
| Dependency policy: offline release, packaging, browser, platform checks | Separate executable, no library mode, `_exit` on fatal errors | Host interop broke in patch release 2.0.38 | Dormant or pre-launch |
| String-heavy data (qualified names, codepoint sorting) | Linked-list strings, no JSON | Values cross into JS as plain values | 24-bit numbers in HVM2 |
| Parallel speedup | 10–12x on 16 cores, balanced work only | **One core** | Vendor-reported only |

The constraints come from Shape's own documents. The release workflow's verify job runs `shp check` on Linux x64, Linux ARM64, macOS ARM64 and Windows x64 ([RELEASING.md](../RELEASING.md)). "The binary needs neither Bun nor Node" ([README.md](../README.md)). Any engine must pass "offline release, binary packaging, browser, and supported-platform checks" ([rule-evaluation.md](../docs-site/src/content/docs/inside-shape/rule-evaluation.md)). Bend's own sources supply the table's other cells: the installer refuses Windows shells ([install.sh](https://bend-lang.com/install.sh)), and 2.0.38 changed constructor tags and export keys for JS hosts ([CHANGELOG](https://github.com/bendlang/bend/blob/main/CHANGELOG.md)). The one route that stays inside Shape's constraints, the JS target, gives up the parallelism that was the reason to want Bend.

The vendor adds its own risk. HOC raised about **$4M in seed funding in 2023** ([Taelin on X](https://x.com/VictorTaelin/status/1743751536465903795)) and lists 11 employees ([PitchBook](https://pitchbook.com/profiles/company/651706-84)). Its own thesis document reported "around $1 million remaining" and a research runway to **the end of 2026** ([hoc_thesis gist](https://gist.github.com/VictorTaelin/5d42e97684ff81f7e507aa5c149b2a64)). Its 2025 crowdfunding had raised $215k by March 2025 ([Taelin on X](https://x.com/VictorTaelin/status/1896617297663406277)).

The synthesis story has weakened over time. HOC first claimed SupGen beat existing synthesizers "by up to 1000x" ([hoc_thesis gist](https://gist.github.com/VictorTaelin/5d42e97684ff81f7e507aa5c149b2a64)); by September 2026 the claim was "10x or so. This is unpublished yet" ([HN 49753179](https://news.ycombinator.com/item?id=49753179)). HOC's paid proving agent describes itself as "a thin harness around models from Anthropic, OpenAI and others. The specialized models and SupGen ship in future updates" ([bend-lang.com/bender](https://bend-lang.com/bender)). For planning purposes, SupGen does not exist.

## Interaction-net sharing targets redundancy that Shape's workload lacks

The theory behind HVM does offer something real, but Shape already has it. Interaction nets are strongly confluent. Lafont proved that every reduction order reaches the same normal form in the same number of steps ([Lafont 1997](https://doi.org/10.1006/inco.1997.2643)), and HVM2 keeps that guarantee with small exceptions ([HVM2 paper](https://raw.githubusercontent.com/HigherOrderCO/HVM/main/paper/HVM2.pdf)). For a deterministic checker this sounds attractive. Shape, though, gets the same property from ordinary code: codepoint-sorted output, canonical witnesses, no clock reads, and a test that requires byte-identical output when declaration order is permuted ([determinism.test.ts](../packages/shp-checker/src/behavioural/determinism.test.ts)). So determinism does not set HVM apart.

The rest of the theory pulls in the wrong direction. "Optimal" reduction means Lévy-optimal: it never duplicates a redex (a reducible expression) that came from the same place in the source term. It is not memoization. One optimal reducer's documentation is explicit that "the avoidance of redex duplication is relative to the initial term, not to the computational pattern exhibited by the term" ([Optiscope](https://github.com/etiamz/optiscope)). So two identical reachability queries issued in different places are not shared. HVM skips the costly bookkeeping of full optimal reduction by forbidding one pattern: "a higher-order lambda that clones its variable can not be cloned" ([HVM2 paper](https://raw.githubusercontent.com/HigherOrderCO/HVM/main/paper/HVM2.pdf)). That keeps HVM fast but leaves the higher-order sharing advantage unused by first-order fact and graph code, which is all Shape has. Shape's graph rules need visited sets, which are shared mutable state. HVM2's own paper puts single-thread HVM2 at **5x slower than GHC, rising to 100x for loops and mutable arrays**. An optimized optimal reducer insertion-sorted 10,000 elements about **70x slower** than unoptimized Haskell ([Optiscope](https://github.com/etiamz/optiscope)). No peer-reviewed work was found that uses interaction nets as the engine for Datalog, graph reachability, cycle detection or model checking. Using them for Shape's rules would be original research, not adoption of known practice.

The one workload whose shape matches superposition is evaluating many variants with shared work. Superposition holds many candidate values in one term, so computation that does not depend on the choice is done once. All the evidence for it comes from vendor toy benchmarks against weak baselines. ADD-CARRY needed 36k interactions against 262M by brute force, but only with a hand-written template, and the author added that "the general problem is still exponential" ([ADD-CARRY gist](https://gist.github.com/VictorTaelin/d5c318348aaee7033eb3d18b0b0ace34)). An XOR-XNOR search ran in 0.0085 s against 2.8 s for a Haskell enumerator ([DPS gist](https://gist.github.com/VictorTaelin/7fe49a99ebca42e5721aa1a3bb32e278)) that, as an independent commenter pointed out, did no pruning ([SO 78843195](https://stackoverflow.com/questions/78843195/can-this-discrete-program-search-have-improved-asymptotics-in-haskell)). Established techniques attack the same redundancy and have peer-reviewed results. AccMut groups mutants that are equivalent given the current state and ran **8.95x faster than mutant schemata** ([AccMut](https://arxiv.org/abs/1702.06689)). Lifted Datalog analyses every product variant in one pass and reports being "about 7.4 billion times faster than brute-force" on BerkeleyDB, where the baseline enumerates exponentially many products ([lifted Datalog, FSE'19](https://arxiv.org/html/1907.02192v2)).

For Shape the better route is analytic. E10 found that its largest operator, 79,415 add-effect mutants, "is predicted exactly by one fact: a mutant survives iff its component already grants that effect" ([E10 report](../experiments/verus-probes/e10/REPORT.md)). That is a single join. Edge mutants also have a closed form. Adding `u → v` creates a forbidden `s → t` path exactly when `s` already reaches `u` and `v` reaches `t`, and it creates a cycle exactly when `v` reaches `u`. One transitive closure of a roughly 24-node component graph therefore answers all 502 `calls` mutants at once. Shape's canonical BFS is still needed, but only to build witnesses for the mutants that are killed.

| Job in Shape | Established technique | What HVM-style sharing adds |
|---|---|---|
| Grant, forbid and effect rules | Direct TS (current); semi-naive Datalog if rules multiply | No delta mechanism, no published Datalog engine |
| Forbidden paths, hypercycles | Tarjan SCC and BFS with visited sets | The affine model works against shared visited sets |
| Tens of thousands of mutants | In-process incremental checking, closed-form joins, lifted Datalog | Toy, vendor-only evidence; "still exponential" |
| Proposing new claims | Bounded enumeration in TS; LLM drafting plus deterministic checks | SupGen unreleased |

## Every candidate integration loses to a cheaper, proven alternative

Six concrete ways Bend or HOC technology could enter Shape were scored against Shape's constraints and against the strongest alternative for each job:

| Candidate | Fits Shape's constraints? | Effort | Ceiling on benefit | Stronger alternative | Verdict |
|---|---|---|---|---|---|
| Run rule evaluation on Bend/HVM | No natively; JS target is single-core | XL | ≤8–35 ms per run | Direct TS (current); Rust Datalog crate to WASM if the decision reopens | Ruled out |
| Superposed mutation and variant batches | Only as an isolated Linux research harness | L–XL | Small next to the existing 17–23x | In-process incremental checker, closed-form analysis | Not worth it |
| SupGen-style synthesis of claims | Advisory output only; SupGen unreleased | M–L | Search spaces of hundreds | TS claim mining; LLM drafting plus checking | Borrow the idea in TS |
| Bend 2 / Kind proofs of checker rules | Research only | XL | Proves a second model, not the shipped code | Verified certificate checker in Verus or Lean | Research only |
| Shape modelling Bend programs | Already works via `bend("…")` references | S–M | No demand found | Trust-marker probe | Wait for demand |
| `fold`/`bend` structured evaluation (idea only) | Yes, no dependency | S–M | Order independence; fix for the hypercycle hotspot | — | Adopt internally |

Moving rule evaluation fails on semantics as well as speed. Shape's fact stream "is not a complete rule database". `rule` facts lack conditions, change events are not facts, and final-forbid precedence and canonical witness selection live in control flow ([rule-evaluation.md](../docs-site/src/content/docs/inside-shape/rule-evaluation.md)). The repository's Datalog spike shows the danger. It reproduces `missing_grant` with one anti-join, yet its tests confirm it reports a `missing_grant` that production correctly suppresses for a `HardDelete` on an `AppendOnly` resource ([datalog spike](../packages/shp-checker/src/experiments/datalog-rule-engine-spike.ts)). Re-encoding 18 rules in Bend would create the "two semantic representations of the same model" that Shape's July 2026 decision explicitly rejected. Comparable tools support that call. ArchUnit and dependency-cruiser check layer and cycle rules with direct code over an in-memory graph ([ArchUnit](https://www.archunit.org/userguide/html/000_Index.html); [dependency-cruiser](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md)). Datalog engines belong at CodeQL scale, with millions of tuples ([CodeQL](https://codeql.github.com/docs/ql-language-reference/evaluation-of-ql-programs)). If Shape ever needs an engine, Rust crates such as Ascent, which ships a `wasm-bindgen` feature, fit its existing Rust/WASM kernel experiment far better ([crates.io ascent](https://crates.io/crates/ascent)).

Proving the checker in Bend would prove the wrong artifact. Bend 2's laws "are proven about Bend's semantics. The backends can still differ" ([README](https://github.com/bendlang/bend#limitations)). A Bend model of Shape's rules would be a second implementation, and nothing would prove that it matches the TypeScript that ships. Affine values, the lack of type classes and linked-list strings would also make Shape's data awkward to encode. The established pattern is to leave the evaluator untrusted and verify a small checker for its output. CakeML's verified checkers audit results in the international SAT competitions ([CakeML](https://cakeml.org/checkers.html)). A Lean 4 checker verifies Datalog proof trees from Nemo or Soufflé ([ITP 2025](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ITP.2025.36)). Verus has verified systems code at kernel scale ([Verus, SOSP'24](https://dl.acm.org/doi/abs/10.1145/3694715.3695952)). Shape's positive diagnostics are easy to certify this way: a `forbidden_path` witness is just a list of edges to check. Pass results ("no forbidden path exists") need either a closed-set certificate or a verified kernel. That work fits the Verus direction Shape is already exploring.

Synthesis fails for a structural reason. `shp check` deliberately has no knowledge of code semantics, so it offers nothing to synthesise against. "Agents scaffold, humans review, and the checker rejects incoherent claims" ([design-rationale.md](../docs-site/src/content/docs/inside-shape/design-rationale.md)). The useful search is over candidate claims checked against the model itself, and E10 shows it is needed. **65 of 79 resources** have no provider-exclusivity rule, and 897 mutants where a non-owner provides an owned resource pass ([E10 report](../experiments/verus-probes/e10/REPORT.md)). Enumerating the 79 `forbid provides … except <owner>` and 552 `forbid path A -> B` candidates, keeping those the current model passes, and ranking them by E10 kills takes seconds in TypeScript. For drafting, the evidence shows the bottleneck is judging candidates, not generating them. Only **42.3%** of verifier-accepted Verus contracts pass all semantic checks ([VerusEval](https://arxiv.org/abs/2610.26464)). Shape's vacuity and loosening checks are exactly that kind of judgment.

Modelling Bend codebases already works and has no users. The grammar's `SourceRef` accepts any `language("path")` ([shape.langium](../packages/shp-checker/src/language/shape.langium)). A scratch model citing `bend("src/Game.bend#Game.reset")` produced the expected forbidden-effect error. Only `shp ast` drafting lacks Bend support ([source-languages.ts](../packages/shp-checker/src/source-languages.ts)). None of the repository's 166 issues and pull requests mentions Bend or HVM ([local survey](../research_notes/Bend%20and%20HVM%20for%20Shape/shape_codebase_fit.md)).

## Three Bend ideas are worth borrowing, and the bigger wins are in TypeScript

The first idea is Bend 2's `LAWS.bend` workflow. Its README calls it "`AGENTS.md` backed by proof": a human-reviewed law file, proofs written by agents, and a proof gate on every edit ([README](https://github.com/bendlang/bend)). That is Shape's bet applied to code instead of architecture, so it supports Shape's design direction. Bend's early experience offers two lessons Shape can take directly. First, "a proof closes the gap between implementation and formal statement; it cannot close the gap between the formal statement and human intent" ([hackyourworld.com](https://hackyourworld.com/bend-proof-ai-code-limitations/)), so claim files need ownership and loosening checks. Shape's `--check-loosening` already provides those checks, and they should stay a priority. Second, in issue #1482 the expression `3n * 0n+0n + 5n` parsed as `3*(0+(0+5))`. The kernel stayed sound while a reader misread the theorem ([bendlang/bend#1482](https://github.com/bendlang/bend/issues/1482)). For Shape, an unambiguous surface syntax and diagnostics that explain themselves are part of the assurance story, not polish. Bend's checker is also fast because it is fully explicit and does no inference ([HN 49753179](https://news.ycombinator.com/item?id=49753179)). That supports Shape's fixed rule forms and argues against ever adding user-visible recursion to `.shape` rules.

The second idea is Bend's divide-and-fold structure. Each rule can be written as a pure map over independent units (functions, hyperedges, component vertices) followed by an associative, commutative fold into a canonically sorted diagnostic set. That makes order independence a stated property rather than an accident of the final sort. A small helper in `checker/rules/` plus a property test with shuffled unit order, built on the existing determinism test, prepares Shape for parallel or incremental evaluation without adding a dependency. The same structure, a minimum under a total order, justifies the hypercycle pruning described earlier.

The third idea is governance of trust markers. Bend's `@unsafe` and `def f?` turn off termination checking, and its proof bounty excludes unsafe code and foreign-function calls ([Taelin on X](https://x.com/VictorTaelin/status/2104240438127288652)). Shape's Verus probes found that **49% of commits contain a trust event** and that a per-file count diff catches 85% of them. They also found a solver can tell when an edited contract is looser, proving 42 of 44 equivalences ([verus-probes README](../experiments/verus-probes/README.md)). A Bend probe that counts escape hatches and flags loosened `LAWS.bend` edits would be the most Shape-like thing to offer Bend users. It belongs in `experiments/` until someone asks for it.

The bigger wins need no new runtime, and engineering time spent on Bend would come out of them:

| Action | Payoff | Effort |
|---|---|---|
| Rewrite `compareCodepointStrings` to compare without allocating | Removes most of the 958 ms fact sort; helps every fact consumer and any future backend | S |
| Run mutation harnesses inside one `IncrementalShapeChecker` | Measured 17–23x per mutant; E10's single-run mode drops from about 9–12 minutes to under 1 on 4 workers | S |
| Answer mutants in closed form (one join for effects, base-graph reachability for edges) | One transitive closure settles all 502 `calls` mutants | S–M |
| Cache parsed files by content hash, then parse in parallel workers | Targets the roughly 70% parse share, as TypeScript 7 does | M |
| Prune hypercycle search sources, with witness-parity tests | Bounds the N^2.7 failing-model case | M |
| Claim-mining advisory command | Proposes rules that kill E10's surviving mutants | M |
| Verified witness checker in Verus or Lean | Assurance for shipped diagnostics, aligned with the Verus work | M–L |
| Extend `ExperimentalSemanticKernelIsolation` to `callbacks` and `coordinated_call` | Closes the isolation leaks E10 found before any new backend lands | S |

The isolation row matters for any experimental backend, Bend included. E10 showed that the current rule lets direct `calls` edges from four components, and every `callbacks` or `coordinated_call` route, reach the kernel unchecked ([E10 report](../experiments/verus-probes/e10/REPORT.md); [runtime.shape](../shape/runtime.shape)).

## Conclusion

The question of whether Bend is a force multiplier comes down to where Shape spends its effort. The answer is parsing, review attention and the quality of claims, not computation. Interaction nets, GPUs and superposition multiply computation, so they have nothing to act on here. The more interesting finding is that Bend 2 and Shape have converged from opposite directions on one product idea: reviewed specification files that gate agent-written changes. Bend applies it at the code level with proofs. Shape applies it at the architecture level without reading code. The two are complementary layers, not competing engines. If a relationship forms, it is more likely to be Shape governing Bend projects (their law files, escape hatches and loosening edits) than Shape running on Bend.

Three conditions would reopen the integration question, and none is close. First, Shape would need a workload of millions of pure, structurally shared variants with little relational or incremental structure, plus a GPU to run them on. Second, Bend 2 would need native Windows support, a stable host interface and an embeddable library mode. Third, SupGen would need a public release benchmarked against named synthesizers. The last is the only event that could change the synthesis verdict, and HOC's published claims for it have shrunk each year. Until one of these changes, the cheapest way to get more out of Shape is to fix a string comparator, keep the checker process alive between checks, and put proof effort into verifying Shape's own witnesses.
